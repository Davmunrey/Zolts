# 23 · Security register

**There have been no security incidents, because there is no production system and no customer data.** Everything below is either a control that exists and is tested, a defect with a security dimension found in development, or a risk that is open and named.

A register that opened with a list of "incidents resolved" for a pre-production repository would be theatre. This one states what is enforced, what is enforced by a test, and what is currently accepted.

## Posture in one table

| | State |
|---|---|
| Production deployment | **None.** The runtime is not deployed (`docs/20`) |
| Customer data held | **None** |
| Personal data processed | None in production; the demo fixture is synthetic and generated by `scripts/build_fixture.py` |

The runtime needs three — `ZOLTS_DATABASE_URL`, `ZOLTS_APP_DATABASE_URL`, `ZOLTS_SECRET_KEY` — plus `CRON_SECRET` on Vercel, where the worker is a cron (ADR-041); the release job needs the same three and `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID` as repository secrets. All are the founder's to set, and none passes through a chat, an issue or a file (`docs/20`) |
| Dependency scanning | Socket Security on every pull request (alerts and project report) |

## Controls, and the test that holds each one

A control with no test is an intention. Each row names the check that fails if the control is removed.

### Tenant isolation

| Control | Held by |
|---|---|
| `force row level security` on every tenant-scoped table — the owning role is bound by the policy too | `test_runtime_isolation.py`; preflight reports it |
| A query that sets no tenant **raises** rather than returning an empty set | `test_a_query_without_a_tenant_raises_rather_than_returning_nothing` |
| A tenant cannot read another's rows | `test_a_tenant_reads_only_its_own_rows` |
| A tenant cannot write or update a row into another tenant | two tests |
| The application role cannot bypass RLS and is not a superuser | preflight `application role` |
| The application role cannot read invitations | `test_the_application_role_cannot_read_invitations` |
| The privileged surface is two `security definer` functions returning identifiers only | ADR-008 |
| CI fails a run that skipped the isolation tests | `test_ci_never_reports_green_having_skipped_these` |
| The two documents a partner signs against — the baseline and the incrementality report — cannot be updated or deleted by the serving role | `test_the_serving_role_cannot_restate_a_frozen_report_or_a_baseline` (ADR-043) |

**Why an empty set is refused rather than returned:** an empty set is indistinguishable from a correct answer, which is how an isolation bug survives a suite that asserts on results.

### Credentials and keys

| Control | Held by |
|---|---|
| Connector credentials sealed with AES-GCM, key derived from `ZOLTS_SECRET_KEY` | `runtime/crypto.py`; `test_connector_secrets_are_not_readable_from_the_database` |
| The sealing key can be replaced without downtime or data loss, and the runtime reports what is still on the old one | `runtime/rotation.py`; `test_key_rotation.py` (16 tests, including the half-finished rotation and the credential no key opens); preflight `sealed credentials` |
| An API token is never stored — only its SHA-256 and a display prefix | `test_a_token_is_never_listed` |
| A leaked key can be revoked and stops working immediately | `test_a_leaked_key_can_be_revoked_and_stops_working` |
| Revoking never deletes the row, so the audit survives the revocation | `test_revoking_never_deletes_the_row` |
| A key cannot revoke itself | `test_a_key_cannot_revoke_itself` |
| Rotation issues before it revokes, so there is no window with no valid key | `test_rotation_issues_before_it_revokes` |
| Keys are tenant-scoped | `test_keys_are_tenant_scoped` |
| Revoking a key ends every browser session it opened | `test_revoking_the_key_ends_the_sessions_it_opened` |

### Browser session

The console is the one surface a person opens in a browser, so it is the one that needs session security rather than bearer tokens.

| Control | Held by |
|---|---|
| The cookie is **not** the API key — a long-lived bearer credential in a cookie is in browser storage, in history, and on every request to the origin forever | `test_the_cookie_is_not_the_api_key` |
| The session token is never stored | `test_the_session_token_is_never_stored` |
| Double-submit CSRF token on every state-changing call | three tests: missing, forged, and the valid case |
| Reads do not require the token; the key header is exempt | two tests |
| Sessions expire, and an expired session is refused | `test_an_expired_session_is_refused` |
| A session carries only the scopes of the key that opened it | `test_a_session_carries_only_the_scopes_of_the_key_that_opened_it` |
| Sessions are tenant-scoped | `test_sessions_are_tenant_scoped` |

### Content Security Policy

The static demo ships a CSP generated from the hash of the page it serves, not hand-written.

| Directive | Value | Consequence of getting it wrong |
|---|---|---|
| `script-src` | `'self'` plus the SHA-256 of each inline block | An injected script executes |
| `connect-src` | `'none'` | The demo cannot exfiltrate to anywhere |
| `object-src`, `base-uri`, `form-action` | `'none'` | Plugin execution, base-tag hijack, form redirection |
| `frame-ancestors` | `'self'` | Clickjacking |
| `img-src` | `'self' data:` | |

`scripts/build_site.py` regenerates the hashes and CI fails if the committed policy is stale — the same drift check that caught D-18.

### Deploy-time refusal

`python3 -m runtime.cli preflight` is the release command, so a misconfigured runtime fails the deploy instead of serving. Ten checks; the security-bearing ones:

| Check | Refuses when |
|---|---|
| `secret key` | The key is a value published in this repository — **verified in CI by asserting the production preflight fails with the CI key** |
| `application role` | The role is a superuser or can bypass RLS |
| `forced row-level security` | Any tenant-scoped table is not FORCE-protected |
| `unscoped reads refused` | A query with no tenant returns rows instead of raising |
| `encryption in transit` | The connection crosses a network unencrypted |
| Production on Vercel is released only by the job that migrates and runs preflight in production mode first; the platform's own deploys of `main` are off, so a push cannot go around it | `deploy-vercel.yml`; `vercel.json`; `test_production_is_released_only_through_the_workflow_that_migrates` |

## Findings with a security dimension

Cross-referenced to `docs/22`. None reached a customer.

| ID | Finding | Why it is a security finding | Status |
|---|---|---|---|
| D-01 | Schema `zolts` shadowed by role `zolts`; a second migration run silently duplicated every table into the shadowing schema | Queries returning data from the wrong copy, with no error. An integrity failure that no assertion on results would catch | **Patched** — schema renamed `zolts_internal`, `search_path` pinned per connection, test bars a schema named after a plausible role |
| D-02 | Every reply counted as positive; a written opt-out was invisible and the person stayed contactable | Contacting someone who asked not to be contacted. A GDPR/ePrivacy exposure, not a metrics bug | **Patched** — an unsubscribe found in text goes through the *same* suppression path as a provider's unsubscribe event, because two suppression mechanisms would have to agree forever |
| D-22 | A policy decision could be written with no reason | The audit trail that answers "why was this person not contacted" could be null. Product invariant 3 was two-thirds enforced | **Patched** — migration 018 makes it `not null` with a non-blank check; the code raises `DecisionWithoutAReason` |
| D-23 | Nothing structurally prevented an agent from importing a connector and contacting someone directly | Product invariant 1 was a habit, not a property. The failure mode is an email nobody approved and no policy decision recorded | **Patched** — an import bar under `runtime/agents/`, verified by mutation |
| D-30 | The application role lacked `usage` on a sequence, so an insert was denied | Least privilege applied too far is an outage; the fix is a deliberate grant, not a broader role | **Patched** — grants on all sequences, plus a test that every sequence is usable |
| D-21 | `docs/02` claimed zero-copy over the customer's warehouse in the present tense; nothing implements it | A buyer's security review reads that ADR and asks to see the connector. The exposure is to diligence, not to an attacker | **Corrected** — the document says what ships; decision 29 holds the revisit |

## What would be a real incident

For the register to be useful later, the threshold is stated now. Any of these is an incident and gets an entry with a timeline:

- Any read or write across a tenant boundary in a deployed system
- Any external action — a send, a CRM write — taken without a recorded policy decision
- Any disclosure of a connector credential, sealed or otherwise
- Any contact of a person on a suppression list
- Any unauthorised access to the console or the API
- Any dependency advisory that Socket flags as reachable from this code
